## 1. 요구사항 분석

### 1-1. 요구사항 요약

| ID | 기능 | 행위자 | 입력 | 출력 | 특이사항 |
|---|---|---|---|---|---|
| REQ-PRED-001 | AI 폐렴 예측 | 의료인·개발팀·연구자 | 진료기록 ID (`AI 예측 결과보기` 버튼) | 폐렴 여부, Confidence, 히트맵 URL(선택) | **진료기록 등록 시 업로드한 X-Ray 사용**, 같은 기록·같은 모델 결과가 있으면 **재추론 없이** 저장된 결과 응답 |
| REQ-PRED-002 | 예측 결과 목록 조회 | 의료인·개발팀·연구자 | 진료기록 ID | 고유 ID, 폐렴 여부, Confidence, 히트맵 URL, 예측 수행 일시, 사용한 모델 | 진료기록 상세 화면의 AI 예측 결과 섹션 |
| NFR-PRED-001 | 모델 평가 기준 | - | - | - | Recall ≥ 0.90 (최소), Accuracy ≥ 0.80 (보조) |
| NFR-PRED-002 | 성능 | - | - | - | 모든 API 3초 이내 |

### 1-2. 행위자와 권한 분석

요구사항은 두 기능 모두 행위자를 "사내 **의료인, 개발팀, 연구자** 권한을 가진 유저"로 표현한다. 이는 세 부서 전체이므로 부서로 제한하지 않는다. 5일차의 조회 API와 같은 기준이다.

| 권한 이름 | 조건 | 적용 API |
|---|---|---|
| 스태프 이상 (`StaffUser`) | `role ∈ {staff, admin}` | 예측 실행, 결과 목록, 히트맵 조회 |

- 대기자(`pending`)는 403이다 (4일차 정의: 대기자는 마이페이지 외 접근 불가).
- 예측 실행은 DB에 결과 행을 **생성**하지만, 진료 데이터를 바꾸지 않고 이미 등록된 이미지를 판독만 하므로 의료진(`MedicalStaffUser`)으로 제한하지 않는다 (D3).

### 1-3. 데이터 모델 분석

```text
patients (환자)
 └─(1:N)─ medical_records (진료기록)
           ├─(1:N)─ xray_images (X-Ray 이미지, API는 기록당 1장 운영 - 5일차 D15)
           └─(1:N)─ ai_analysis_results (AI 판독 결과)  ← 이번 작업 대상
```

**`ai_analysis_results` 현재 구조 (3일차 생성)**

| 컬럼 | 타입 | 제약 | 요구사항 대응 |
|---|---|---|---|
| `id` | BigInteger | PK | 고유 ID |
| `record_id` | BigInteger | FK → `medical_records.id` `ON DELETE CASCADE` | 어느 진료기록의 결과인지 |
| `is_pneumonia` | Boolean | NOT NULL | 폐렴 여부 |
| `confidence` | Numeric(5, 2) | NOT NULL | Confidence (%, 예: `91.50`) |
| `heatmap_url` | String(255) | **NOT NULL** | 히트맵 이미지 URL (**요구사항은 선택사항**) |
| `ai_model` | String(50) | NOT NULL | 사용한 모델 |
| `created_at` / `updated_at` | DateTime | `TimestampMixin` | 예측 수행 일시 |

| 요구사항 | 현재 모델 | 차이 |
|---|---|---|
| 히트맵 URL **선택사항** | `heatmap_url` NOT NULL | 히트맵을 만들지 않으면 저장 시 DB 오류 → **nullable로 변경** (D4) |
| 같은 기록·같은 모델은 한 번만 추론 | `(record_id, ai_model)` 제약 없음 | 동시에 두 번 누르면 결과가 2건 생길 수 있음 → **UNIQUE 제약 추가** (D6) |
| 이미지 교체 시 이전 결과 무효 | 5일차에 구현됨 | 진료기록 수정에서 이미지 교체 시 AI 결과·히트맵 파일 삭제 (5일차 D15). 추가 작업 없음 |
| 환자·진료기록 삭제 시 결과 삭제 | 5일차에 구현됨 | DB `CASCADE` + 히트맵 파일 정리. 정리 코드가 이미 `heatmap_url`이 비어 있는 경우를 건너뛴다 (`if path`) |

### 1-4. 프론트엔드 계약 분석

저장소에 AI 예측 화면과 호출 코드가 **이미 있다**. API는 화면이 호출하는 형식을 따른다 (5일차 D1과 같은 원칙).

| 화면 동작 | 호출 (`static/apis.js`) | 화면이 사용하는 응답 필드 |
|---|---|---|
| `AI 예측 결과보기` 버튼 | `POST /medical-records/{recordId}/predict` | 없음. 성공하면 알림 후 상세 화면을 다시 그린다 |
| 상세 화면 진입 시 결과 목록 | `GET /medical-records/{recordId}/analyses` | **배열**의 `created_at`, `is_pneumonia`, `confidence`, `ai_model` |

- 상세 화면(`renderRecordDetail`)은 진입할 때마다 `/analyses`를 호출한다. **이 API가 없으면 지금 진료기록 상세 화면 자체가 열리지 않는다** → 목록 API는 결과가 없어도 `200 []`을 반환해야 한다.
- 목록 화면은 `analyses.length`, `analyses.map`을 쓴다 → 응답은 **배열**로 한다.
- 화면은 `confidence` 뒤에 `%`를 붙여 표시한다 → `confidence`는 **0~100 단위**로 응답한다.
- 오류는 `error.detail`을 읽어 `AI 예측 실패: {detail}`로 표시한다 → 오류 형식은 `{"detail": ...}`로 유지한다.
- 현재 표에는 히트맵 열이 없다. 히트맵을 만들기로 하면 화면에 열을 추가한다 (11-2절).

## 2. 공통 규칙

### 2-1. 기본 규칙

5일차 2-1절 규칙(기본 경로 `/api/v1`, Bearer 인증, `{"detail": ...}` 오류, UTC 저장·ISO 8601 `Z` 응답, 개인정보 로그 금지)을 그대로 따른다. 이번 작업에서 추가하는 규칙은 다음과 같다.

| 항목 | 규칙 |
|---|---|
| 요청 본문 | 없음. 예측에 쓸 이미지는 진료기록에 저장된 X-Ray를 서버가 찾아 사용한다 |
| Confidence | **예측한 클래스의 확률**을 0~100(%)으로, 소수 둘째 자리까지 (`Numeric(5,2)`) |
| 히트맵 URL | 파일 위치가 아니라 **조회 API 경로**를 응답 (`/api/v1/medical-records/{record_id}/analyses/{analysis_id}/heatmap`), 히트맵이 없으면 `null` |
| 모델 이름 | 서버 설정 `AI_MODEL_NAME` 값 하나. 결과 행의 `ai_model`에 저장하고 재사용 판단 기준으로 쓴다 |

### 2-2. 응답 스키마

**`AnalysisResultResponse`** (예측 실행·목록 공통)

| 필드 | 타입 | 설명 |
|---|---|---|
| id | integer | 예측 결과 고유 ID |
| record_id | integer | 진료기록 ID |
| is_pneumonia | boolean | 폐렴 여부 |
| confidence | number | 판독 신뢰도 (%), 예: `91.5` |
| heatmap_url | string \| null | 히트맵 조회 API 경로. 히트맵이 없으면 `null` |
| ai_model | string | 사용한 모델 이름 |
| created_at | datetime | 예측 수행 일시 |

**Confidence 계산 규칙**

모델 출력이 폐렴 확률 `p`(0~1) 하나라고 할 때:

| 판정 | 조건 | confidence |
|---|---|---|
| 폐렴 | `p ≥ threshold` | `p × 100` |
| 정상 | `p < threshold` | `(1 − p) × 100` |

- `threshold` 기본값은 `0.5`이고 설정값(`AI_PNEUMONIA_THRESHOLD`)으로 둔다. Recall 기준을 맞추려고 낮출 수 있다 (9절).
- 예: `p = 0.87` → 폐렴, `87.00` / `p = 0.12` → 정상, `88.00`
- 이 계산은 1단계 예측 모듈이 하고, API는 받은 값을 저장만 한다 (5절).

### 2-3. 오류 코드

| 코드 | 상황 | detail |
|---|---|---|
| 401 | 토큰 없음·만료·위조 | `인증 정보가 유효하지 않습니다.` |
| 403 | 대기자 | `접근 권한이 없습니다.` |
| 404 | 진료기록 없음 | `진료기록을 찾을 수 없습니다.` |
| 404 | 진료기록에 X-Ray가 없거나 파일이 없음 | `X-Ray 이미지를 찾을 수 없습니다.` |
| 404 | 예측 결과 없음, 히트맵 없음 | `예측 결과를 찾을 수 없습니다.` / `히트맵 이미지가 없습니다.` |
| 409 | 추론 중에 진료기록 이미지가 교체됨 | `X-Ray 이미지가 변경되었습니다. 다시 시도해주세요.` |
| 422 | 경로 파라미터 형식 오류 (`record_id=abc`, `0`) | FastAPI 검증 오류 |
| 500 | 추론 중 예외, DB·저장소 처리 실패 | `AI 예측 중 오류가 발생했습니다.` |
| 503 | 모델이 로드되지 않음 (모델 파일 없음·손상) | `AI 모델을 사용할 수 없습니다. 관리자에게 문의하세요.` |

> `401`은 모든 API에서 공통으로 발생하므로 API별 실패 표에는 생략한다.

## 3. API 목록과 요구사항 추적

| No | Method | 경로 | 기능 | 요구사항 | 권한 | 성공 |
|---|---|---|---|---|---|---|
| ① | POST | `/api/v1/medical-records/{record_id}/predict` | 폐렴 예측 실행 (저장된 결과가 있으면 재사용) | REQ-PRED-001 | 스태프 이상 | 201 (새 추론) / 200 (저장된 결과) |
| ② | GET | `/api/v1/medical-records/{record_id}/analyses` | 예측 결과 목록 | REQ-PRED-002 | 스태프 이상 | 200 |
| ③ | GET | `/api/v1/medical-records/{record_id}/analyses/{analysis_id}/heatmap` | 히트맵 이미지 조회 | REQ-PRED-001·002 (히트맵 URL) | 스태프 이상 | 200 (이미지) |

- ①②의 경로는 프론트엔드 코드에 이미 정해져 있다 (1-4절).
- ③은 히트맵을 만들기로 결정한 경우에만 구현한다 (14절 Q1). 5일차 X-Ray 조회 API(`/xray-image`)와 같은 방식이다.

## 4. 예측 API 상세

### 4-1. 폐렴 예측 실행 `POST /api/v1/medical-records/{record_id}/predict`

| 항목 | 내용 |
|---|---|
| 요구사항 | REQ-PRED-001 |
| 권한 | 스태프 이상 (`StaffUser`) |
| 요청 본문 | 없음 |

**처리 규칙**
1. 진료기록이 없으면 404.
2. 이 진료기록에 **현재 모델 이름(`AI_MODEL_NAME`)으로 저장된 결과가 있으면** 추론하지 않고 그 결과를 `200`으로 응답한다.
3. 없으면 진료기록의 X-Ray 파일로 추론하고, 결과를 저장한 뒤 `201`로 응답한다.
4. 모델 이름이 바뀌면(새 모델 배포) 같은 진료기록이라도 다시 추론한다. 이전 모델 결과는 지우지 않고 목록에 함께 남는다.

**Response `201 Created`** (새로 추론) / **`200 OK`** (저장된 결과 재사용): `AnalysisResultResponse`

```json
{
  "id": 12,
  "record_id": 1,
  "is_pneumonia": true,
  "confidence": 87.12,
  "heatmap_url": "/api/v1/medical-records/1/analyses/12/heatmap",
  "ai_model": "densenet121-v1",
  "created_at": "2026-10-28T05:10:00Z"
}
```

- `201`일 때 `Location: /api/v1/medical-records/1/analyses` 헤더를 반환한다.
- 상태 코드로 새 추론인지 재사용인지 구분할 수 있다. 화면은 둘 다 성공으로 처리한다.

| 실패 | 상황 |
|---|---|
| 403 | 대기자 |
| 404 | 진료기록 없음, X-Ray 이미지(행 또는 파일) 없음 |
| 409 | 추론하는 동안 이미지가 교체됨 (6-1절) |
| 422 | `record_id` 형식 오류 |
| 500 | 추론 중 예외, 저장 실패 |
| 503 | 모델 미로드 |

### 4-2. 예측 결과 목록 `GET /api/v1/medical-records/{record_id}/analyses`

| 항목 | 내용 |
|---|---|
| 요구사항 | REQ-PRED-002 |
| 권한 | 스태프 이상 (`StaffUser`) |
| 정렬 | 예측 수행 일시 **최신순** (`created_at DESC, id DESC`) |

**Response `200 OK`**: `AnalysisResultResponse` **배열**

```json
[
  {
    "id": 12,
    "record_id": 1,
    "is_pneumonia": true,
    "confidence": 87.12,
    "heatmap_url": "/api/v1/medical-records/1/analyses/12/heatmap",
    "ai_model": "densenet121-v1",
    "created_at": "2026-10-28T05:10:00Z"
  }
]
```

| 실패 | 상황 |
|---|---|
| 403 | 대기자 |
| 404 | 진료기록 없음 (결과가 없으면 `200 []`) |

- 요구사항의 "흉부 X-Ray 사진"은 같은 화면이 이미 X-Ray 조회 API(5일차 5-4절)로 표시하므로 목록 응답에 다시 담지 않는다.
- 진료기록 1건의 결과 수는 사용한 모델 수만큼만 생긴다 (D6). 페이지네이션은 하지 않는다.

### 4-3. 히트맵 이미지 조회 `GET /api/v1/medical-records/{record_id}/analyses/{analysis_id}/heatmap`

| 항목 | 내용 |
|---|---|
| 요구사항 | REQ-PRED-001·002의 히트맵 URL |
| 권한 | 스태프 이상 (`StaffUser`) |
| 응답 | `image/png` 바이너리, `Cache-Control: no-store` |

| 실패 | 상황 |
|---|---|
| 403 | 대기자 |
| 404 | 진료기록 없음, 결과 없음, **결과가 다른 진료기록 소속**, 히트맵 없음(`null`), 파일 없음 |

- `analysis_id`만으로 찾지 않고 `record_id`와 **함께** 조건을 건다. 다른 기록의 결과 ID를 넣어 조회하는 것을 막는다.
- 화면은 X-Ray와 같은 방식(`fetch` + Blob)으로 표시한다 (5일차 6-2절).

## 5. 1단계 예측 모듈 인터페이스

1단계(`worker/model.py`)와 2·3단계(API)는 **아래 약속만 지키면 서로의 내부 구현을 몰라도 된다.** 1단계 담당자는 이 형태로 함수를 제공하고, API는 이 함수만 호출한다.

### 5-1. 제공할 것

```python
# worker/model.py
from dataclasses import dataclass
from pathlib import Path

from PIL import Image

MODEL_NAME: str = "densenet121-v1"  # DB ai_model에 저장되는 이름 (50자 이하)


@dataclass(frozen=True)
class PredictionResult:
    is_pneumonia: bool          # 폐렴 여부
    confidence: float           # 예측 클래스의 확률, 0~100 (2-2절 계산 규칙)
    heatmap: Image.Image | None  # 히트맵 이미지. 만들지 않으면 None


def load_model() -> None:
    """모델 파일을 읽어 메모리에 올린다. 서버 시작 시 한 번만 호출된다.
    파일이 없거나 손상되면 예외를 올린다."""


def is_loaded() -> bool:
    """모델이 메모리에 올라가 있는지"""


def predict(image_path: Path) -> PredictionResult:
    """X-Ray 이미지 한 장을 전처리하고 예측한다.
    동기 함수다. API는 스레드풀에서 호출한다 (8절)."""
```

### 5-2. 역할 분담

| 할 일 | 담당 | 이유 |
|---|---|---|
| 모델 파일 로드, 전처리(크기·채널·정규화), 추론, confidence 계산, 히트맵 생성 | **1단계 (`worker/`)** | 학습 때와 똑같은 전처리를 알고 있는 쪽이 맡는다 |
| 진료기록·이미지 경로 찾기, 저장된 결과 재사용, 히트맵 파일 저장, DB 저장, 응답 | **3단계 (`app/`)** | 파일 저장 위치·DB·권한 규칙은 API 쪽 규칙이다 |

- `predict`는 **DB와 파일 저장을 하지 않는다.** 이미지 경로를 받아 결과만 돌려준다. 그래서 1단계는 API·DB 없이 단독으로 테스트할 수 있다.
- 히트맵은 파일이 아니라 `Image` 객체로 돌려준다. 저장 위치(`storage/heatmap/...`)와 파일 정리 규칙은 API 쪽이 이미 갖고 있다 (5일차 D18).

### 5-3. 1단계 담당자에게 확인할 값

| 항목 | 확인 내용 | 이 문서에 미치는 영향 |
|---|---|---|
| 모델 이름 | `MODEL_NAME` 값 | 재사용 판단 기준 (D5) |
| 프레임워크 | TensorFlow/Keras 또는 PyTorch | 의존성 추가, Docker 이미지 크기 |
| 모델 파일 크기 | MB 단위 | Git 업로드 방식 (14절 Q3) |
| 히트맵 생성 여부 | Grad-CAM 구현 여부 | ③ API, 화면 열 추가 여부 (14절 Q1) |
| 1장 추론 시간 | 히트맵 포함, CPU 기준 | 3초 충족 여부 (8절) |
| 평가 지표 | 테스트셋 Recall, Accuracy, threshold | NFR-PRED-001 충족 근거 (9절) |

## 6. 주요 처리 흐름

### 6-1. 폐렴 예측 실행

```text
[화면] AI 예측 결과보기 클릭
   │ POST /api/v1/medical-records/1/predict
   ▼
[API] 인증·권한 확인 (StaffUser)
   ▼
[Service] ① 진료기록 조회 ──── 없음 → 404
          ② (record_id, AI_MODEL_NAME) 결과 조회 ── 있음 → 200 (저장된 결과)
          ③ 모델 로드 확인 ──── 미로드 → 503
          ④ 진료기록의 X-Ray 행·파일 확인 ── 없음 → 404
             (이때의 xray_images.id를 기억해 둔다)
          ⑤ predict(이미지 경로)  ← 스레드풀, DB 트랜잭션 밖에서 실행
          ⑥ 히트맵이 있으면 storage/heatmap/{patient_id}/{uuid}.png 저장
          ⑦ 트랜잭션 시작
             - 진료기록의 현재 xray_images.id가 ④와 다르면 → 히트맵 파일 삭제, 409
             - ai_analysis_results INSERT
             - UNIQUE(record_id, ai_model) 위반 (동시 요청이 먼저 저장)
                  → 롤백, 히트맵 파일 삭제, 먼저 저장된 결과를 200으로 응답
          ⑧ 커밋 → 201
   ▼
[화면] "AI 예측이 완료되었습니다." → 상세 화면 다시 그림 → GET /analyses
```

- **추론은 DB 트랜잭션 밖에서 한다.** 추론은 수 초가 걸릴 수 있어서, 트랜잭션 안에서 하면 그동안 DB 연결과 잠금을 붙잡는다.
- 대신 추론하는 동안 다른 사용자가 진료기록 이미지를 교체할 수 있다. 교체되면 이전 이미지로 만든 결과가 새 이미지에 붙게 되므로 ⑦에서 이미지 ID를 다시 확인한다 (D8).
- ⑥ 이후 ⑦·⑧에서 실패하면 저장한 히트맵 파일을 지운다. 삭제까지 실패하면 5일차 파일 정리 작업(`file_cleanup_jobs`)에 기록한다 (5일차 6-4절과 같은 방식).

### 6-2. 서버 시작과 모델 로드

```text
uvicorn 시작
   ▼
FastAPI lifespan 시작 단계 → worker.model.load_model()
   ├─ 성공 → 모델이 메모리에 상주, 모든 요청이 재사용
   └─ 실패 → 오류 로그 기록, 서버는 계속 시작
             (예측 API만 503, 나머지 API는 정상)
```

- 모델을 요청마다 읽지 않고 **서버 시작 시 한 번** 읽는다. 과제 요구("모델을 메모리에 올려두고")와 3초 기준(NFR-PRED-002)을 위한 것이다.
- 모델 파일이 없어도 서버는 뜬다. 환자·진료기록 기능까지 함께 멈추지 않게 하기 위해서다 (D9).
- 테스트에서는 실제 모델 대신 가짜 `predict`를 주입한다 (13절).

### 6-3. 이미지 교체·삭제와 예측 결과

5일차에 이미 구현된 동작이며 변경하지 않는다.

| 동작 | 예측 결과 | 히트맵 파일 |
|---|---|---|
| 진료기록 이미지 교체 (`PATCH`) | 해당 기록의 결과 전체 삭제 | 커밋 후 삭제 |
| 진료기록 삭제 | `CASCADE` 삭제 | 커밋 후 삭제 |
| 환자 삭제 | `CASCADE` 삭제 | 커밋 후 삭제 |

이미지를 교체한 뒤 다시 `AI 예측 결과보기`를 누르면 저장된 결과가 없으므로 새 이미지로 추론한다.

## 7. 보안 설계

| 항목 | 설계 |
|---|---|
| 접근 권한 | 세 API 모두 `StaffUser`. 대기자·비활성 사용자는 접근 불가 |
| 히트맵 저장 위치 | 공개 폴더(`media/`)가 아닌 **비공개 폴더** `storage/heatmap/{patient_id}/{uuid}.png` (설정 `HEATMAP_STORAGE_DIR`). 히트맵은 환자 X-Ray 위에 그린 이미지라 X-Ray와 같은 수준으로 보호한다 (5일차 D10) |
| 히트맵 응답 | 파일 경로가 아니라 조회 API 경로만 응답. DB에는 저장 폴더 기준 상대 경로만 저장 |
| 다른 기록 결과 조회 | 히트맵 조회 시 `record_id`와 `analysis_id`를 함께 조건으로 사용 (4-3절) |
| 모델 파일 | 서버 로컬 파일만 로드한다. 업로드받은 파일이나 URL로 모델을 로드하지 않는다 (pickle·`torch.load`는 신뢰할 수 없는 파일을 열면 코드가 실행될 수 있다) |
| 오류 응답 | 추론 예외의 메시지·스택 트레이스·파일 경로를 응답하지 않는다. 서버 로그에는 `record_id`와 예외 종류만 기록한다 |
| 개인정보 로그 | 이미지 내용, 환자 이름, 예측 결과를 로그에 남기지 않는다 |
| 의료 판단 고지 | 화면에 "AI 예측 결과는 참고용이며 최종 판단은 의료진이 한다"를 표시한다 (14절 Q5) |

## 8. 성능 설계

NFR-PRED-002: 모든 API는 3초 이내 응답한다. 측정 방법은 5일차 8절(요청 수신 완료부터 응답 준비까지, 최대 시간과 p95)을 따른다.

| 대상 | 대응 |
|---|---|
| 모델 로드 | 서버 시작 시 한 번 (6-2절). 요청 처리 시간에 포함되지 않는다 |
| 같은 기록 재요청 | 저장된 결과 재사용 → DB 조회 1~2회로 응답 (REQ-PRED-001) |
| 추론 | `run_in_threadpool`로 실행해 이벤트 루프를 막지 않는다. 추론 중에도 다른 API는 처리된다 |
| 동시 추론 | 동시에 실행되는 추론 수를 세마포어로 제한한다 (기본 1, 설정 `AI_MAX_CONCURRENT_PREDICTIONS`). 메모리 부족과 CPU 경합으로 모든 요청이 느려지는 것을 막는다 |
| 히트맵 | Grad-CAM은 추론 시간이 늘어난다. 1단계에서 측정해 3초를 넘으면 히트맵을 끈다 (14절 Q1) |
| 결과 목록 | `(record_id, ai_model)` UNIQUE 인덱스가 `record_id` 조회에도 쓰인다. 기록당 결과 수가 모델 수만큼으로 작다 |

**3초 예산 (목표치, 측정 후 갱신)**

| 단계 | 목표 |
|---|---|
| 인증·진료기록·결과 조회 | 0.1초 |
| 이미지 읽기·전처리 | 0.2초 |
| 추론 (CPU) | 1.5초 |
| 히트맵 생성·저장 | 0.8초 |
| DB 저장 | 0.1초 |
| **합계** | **2.7초** |

동시 추론을 1개로 제한하면 여러 명이 동시에 새 추론을 요청할 때 뒤 요청은 대기한다. 대기 시간이 3초를 넘으면 미충족으로 기록하고, 비동기 처리(202 접수 + 결과 조회)를 검토한다 (15절 F1).

## 9. 모델 평가 기준

NFR-PRED-001은 API가 아니라 **선택한 모델의 성능 기준**이다. 1단계 담당자가 테스트셋으로 측정한 값을 아래 표에 기록하고, 기준을 넘는 모델과 threshold를 배포한다.

| 지표 | 계산식 | 기준 | 측정값 | 충족 |
|---|---|---|---|---|
| Recall (민감도) | TP / (TP + FN) | **≥ 0.90** (목표 0.95) | (1단계 측정 후 기입) | |
| Accuracy | (TP + TN) / 전체 | ≥ 0.80 (목표 0.90) | (1단계 측정 후 기입) | |

| 항목 | 내용 |
|---|---|
| 평가 데이터 | (데이터셋 이름, 테스트셋 장수, 폐렴/정상 비율 기입) |
| threshold | (기입, 기본 0.5) |
| 우선순위 | **Recall 우선.** FN(폐렴 환자를 정상으로 오진)이 가장 위험하므로, Recall이 0.90 미만이면 threshold를 낮춰 다시 측정한다. 이때 FP가 늘어 Accuracy가 내려가므로 0.80 이상인지 함께 확인한다 |
| 모델 교체 시 | 새 모델은 같은 테스트셋으로 측정해 기준을 넘을 때만 `MODEL_NAME`을 바꿔 배포한다 |

## 10. 설계 결정 기록

| No | 결정 | 검토한 대안 | 선택 이유 |
|---|---|---|---|
| D1 | 주소를 **프론트엔드 코드 기준**(`/predict`, `/analyses`)으로 정함 | REST 형식 `/predictions`로 새로 정의 | 화면이 이미 호출 코드를 갖고 있다. 다르면 상세 화면이 열리지 않는다 (5일차 D1) |

| D3 | 예측 실행 권한을 **스태프 이상**으로 | 의료진(`MedicalStaffUser`)만 | 요구사항이 의료인·개발팀·연구자 모두를 행위자로 적었다. 진료 데이터를 바꾸지 않는 판독이다 |
| D4 | `heatmap_url`을 **nullable로 변경** | NOT NULL 유지 + 빈 문자열 저장 / 히트맵 필수 구현 | 요구사항이 히트맵을 선택사항으로 정했다. 빈 문자열은 "없음"과 "경로"가 섞여 응답 변환에서 실수하기 쉽다 |
| D5 | 재사용 기준을 **`(record_id, ai_model)`** 로 | `record_id`만 | 요구사항이 "같은 모델을 사용하여 저장된 결과"로 정했다. 모델을 바꾸면 새로 추론해 비교할 수 있다 |
| D6 | `(record_id, ai_model)` **UNIQUE 제약 추가**, 위반 시 먼저 저장된 결과 응답 | 조회 후 INSERT만 | 두 번 클릭·동시 요청이 둘 다 "결과 없음"을 보고 2건을 만들 수 있다. 최종 판단은 DB 제약이 한다 (5일차 D14와 같은 원칙) |
| D7 | 새 추론 **201**, 재사용 **200** | 둘 다 200 | 테스트와 로그에서 실제로 추론했는지 구분할 수 있다. 화면은 둘 다 성공으로 처리하므로 영향이 없다 |
| D8 | 추론은 **트랜잭션 밖**, 저장 직전에 **이미지 ID 재확인** | 추론 전체를 트랜잭션 + 행 잠금 | 수 초 동안 DB 연결·잠금을 잡지 않는다. 그 사이 이미지 교체는 ID 비교로 잡아 409로 알린다 |
| D9 | 모델 로드 실패 시 **서버는 시작, 예측 API만 503** | 서버 시작 실패 | 모델 파일 문제로 환자·진료기록 기능까지 멈추면 안 된다. 개발 환경에 모델 파일이 없어도 다른 기능을 개발·테스트할 수 있다 |
| D10 | 예측 모듈은 **경로를 받아 결과만 반환**, 저장은 API가 | `predict`가 DB·파일까지 저장 | 1단계와 3단계를 병렬로 개발하고 각각 단독 테스트할 수 있다 (5절) |
| D11 | confidence는 **예측한 클래스의 확률(%)** | 항상 폐렴 확률 | "정상, 12%"는 정상이라는 판정을 12% 확신한다는 뜻으로 오해된다. 화면이 판정과 확률을 함께 보여준다 |
| D12 | 히트맵을 **비공개 저장소 + 인증 API**로 제공 | `media/` 공개 서빙 | 히트맵은 환자 X-Ray 위에 그린 이미지다 (5일차 D10) |
| D13 | 추론을 **스레드풀 + 동시 실행 수 제한** | 이벤트 루프에서 직접 실행 / 제한 없음 | 직접 실행하면 추론 동안 서버 전체가 멈춘다. 제한이 없으면 메모리 부족이 생길 수 있다 |

## 12. 구현 구조

```text
AH_web_development_assignment/
├── worker/                          # 1단계
│   ├── models/                      # 모델 파일 (.keras / .pt)
│   └── model.py                     # load_model, is_loaded, predict, MODEL_NAME (5절)
└── app/
    ├── apis/
    │   └── analysis_apis.py         # ① ② ③
    ├── schemas/
    │   └── analysis.py              # AnalysisResultResponse
    ├── services/
    │   └── analysis_service.py      # 재사용 판단, 추론 호출, 히트맵 저장, 이미지 재확인, 중복 처리
    ├── repositories/
    │   └── analysis_repository.py   # 결과 조회·저장, 진료기록 X-Ray 조회
    └── core/
        ├── config.py                # AI_* 설정
        └── file_storage.py          # 히트맵 저장 함수
```

- `worker/`는 과제가 정한 위치다. `app/`과 같은 높이에 두고 `from worker import model`로 가져온다.
- 서비스는 `worker.model`을 직접 import하지 않고 **의존성으로 주입**받는다. 테스트에서 가짜 예측 함수로 바꿔 끼우기 위해서다.

**Merge 순서**

```text
① 마이그레이션 (heatmap_url nullable, UNIQUE) + 설정값    ← API·테스트가 모두 사용
        ↓
② 1단계 worker/model.py          ③ 예측 API + 가짜 모델 테스트   (병렬 가능, 5절 인터페이스 기준)
        ↓
④ main.py lifespan 연결 + 실제 모델로 통합 확인 + 성능 측정
        ↓
⑤ (히트맵 구현 시) 히트맵 조회 API + 화면 열 추가
```

## 13. 테스트 시나리오

테스트는 기존 `tests/` 방식(SQLite)으로 작성하고, **실제 모델 대신 가짜 예측 함수**를 주입한다. 가짜 함수는 고정 결과를 반환하고 호출 횟수를 센다.
